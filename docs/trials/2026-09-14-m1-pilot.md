# M1 试点试跑报告（8 题）

日期：2026-09-14。环境：本机 Windows + Node 24.14.1 + .NET 10.0.301，`profile=local`、`isolation=none`。
原始记录：`data/trials/2026-09-14T06-21-13-611Z/`（已忽略）。执行命令：`node scripts/trial.ts`（等价于 `pnpm trial`）。

## 方法

对 8 道试点各跑**两端**：

1. 缺陷端：`task:export` 导出候选工作区 → `createEnvelope` 生成提交信封 → 冻结快照 → 受控执行公开与隐藏检查。
2. 参考端：同样导出后应用 `graders/<ID>/reference.patch` → 冻结 → 执行。

判定标准：参考端必须 `passed`；缺陷端不得 `passed`，且失败项必须与 `manifest.grader.defectDetectors` 完全一致
（否则说明缺陷溢出到未声明的检查上，或隐藏检查与题面不一致）。

## 成本观察（初步校准，非正式成绩）

- TypeScript 题的检查都在 1 秒以内完成；F# 题的成本几乎全部是 `dotnet fsi` 启动与 JIT 开销，而不是检查本身。
- THR-03 两端 32.8 秒来自大量真实线程与带超时的 Barrier：起始版本的两个并发检查各要等满屏障超时。
  这是**缺陷路径**的成本，参考端本身很快；正式预算可以按“参考端 < 5 秒、缺陷端允许更久”分别设定。
- 峰值 RSS 只对 `node` 命令有效（采样器通过 `--import` 注入）。F# 题没有可比的原始内存样本，
  这是当前执行的已知缺口，不能拿“未采集”当成“内存达标”。
- 没观察到超时、内存耗尽或基础设施故障；8 题都在 60 秒预算内完成。

设计难度与实测成本大致相符：简单题是单位置缺陷，中等题多一处状态或解析路径，
困难题需要真实线程或深层输入，极度困难题涉及崩溃恢复与复杂度。
但**难度仍需人工作答与模型试跑校准**，本表只是制作阶段的自评。

## 遗留问题

- 全部结果来自宿主 `profile=local`：没有容器隔离、没有 cgroup 限额、没有网络阻断，不能作为正式成绩。
- 代码质量（50 分）没有接入，8 题的状态都只是“可用验证通过或失败”，总分仍为待定。
- F# 题缺少内存原始样本；`linux-container` 档案在容器运行时可用前被显式拒绝。
- 7 道原仓库集成题、Python 适配器与 Windows/浏览器专项仍未开始（属 M3）。
