# Agent Note: STATE-04 题目包（UI、服务、缓存的故障后一致性）

Status: implemented

## Problem

一次提交要落到服务、缓存、界面三层。失败路径若**只回滚出错的那一层**，之前应用成功的层会留在半成品状态：
界面显示新值、缓存还是旧值、服务已经写入——三层长期不一致，而且下一次成功提交也修不回来。

## Decision

- 冻结 `Coordinator`（`commit`/`applied`）与 `Layer`、`CommitError`；三层都由注入的内存实现驱动。
- 缺陷族只有一条：**回滚不完整**（只回滚失败层，不回滚已应用层）。
- 参考实现记录已应用层并在失败时**按相反顺序**回滚；替代实现先收集撤销闭包再统一执行（结构不同）。
- 检查用事件序列（apply/revert）与三层 `has` 双重断言，既验证顺序也验证最终一致性。

## Alternatives considered

- 让各层自己保证幂等回滚：把契约推给实现方，无法验证宿主是否真的回滚了别的层。
- 引入两阶段提交/事务日志：超出题目范围；本题只考“失败后三层一致”这一条底线。

## Consequences

- 极度困难档 6/12；核心题 37/48。
- 与 STATE-03（检查点重放不可重复入账）、CACHE-03（失效竞态）构成故障一致性主题簇。
