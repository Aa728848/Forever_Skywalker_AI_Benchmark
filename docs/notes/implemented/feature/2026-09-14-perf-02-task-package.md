# Agent Note: PERF-02 题目包（长列表局部更新与渲染范围）

Status: implemented

## Problem

长列表渲染的性能问题几乎都来自**为了一行改动遍历整张表**：先 `map` 全量复制再切片，
列表一万行、窗口五行时代价依然是一万行。这类缺陷在功能测试里完全看不出来，必须用复杂度证据约束。

## Decision

- 冻结 `updateRows(rows, patch, window)` 与 `RenderedRange`。
- 缺陷族只有一条：**全量扫描**（先复制整张列表再切片）。
- 复杂度断言沿用项目既定范式：用 `Proxy` 统计**输入数组访问次数**（含 `length`），
  公开检查断言 `≤ 4×size + 8`，隐藏检查再加一条“10 倍列表长度下访问次数不得增长（比值 ≤ 2）”。
  两条都不依赖计时，因此在任何机器上都稳定。
- 参考实现只在窗口下标上循环；替代实现用 `Array.from` 按窗口下标构造（结构不同）。

## Alternatives considered

- 用真实耗时断言：会被机器负载与 GC 干扰，项目口径明确不用计时判定性能。
- 用 `slice` 的返回值断言“没有全量复制”：无法观察内部是否先复制，必须数访问次数。

## Consequences

- 中等档 11/12；核心题 26/48。
- 到这一轮为止，PERF 家族已有 PERF-01（重复解析）、PERF-02（全量扫描）、PERF-04（极度困难）三道，
  共享同一套“计数输入 + 比值断言”的复杂度证据范式。
