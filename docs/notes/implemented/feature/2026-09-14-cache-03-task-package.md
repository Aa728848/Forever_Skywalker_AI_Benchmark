# Agent Note: CACHE-03 题目包（失效期间的在途旧结果）

Status: implemented

## Problem

带版本号的读取缓存有个经典竞态：**请求刚发出就被失效**。如果结算时无条件把结果写回缓存，
旧数据会重新占据缓存，界面在“已更新”之后又跳回旧值。上一轮我两次都没把这题做出来，
原因不是设计错，而是**注入的缺陷没有真的制造出被测行为**。

## Decision

- 冻结 `VersionedCache`（`get`/`invalidate`/`version`）与 `CachePort`。
- 缺陷族只有一条：**结算时无条件写回缓存**（不校验发起版本）。
- 参考实现：入缓存前比较「发起时的版本」与当前版本，过期结果**只返回不落缓存**；
  替代实现用 generation 计数 + 显式过期判定。
- 契约明确“过期结果仍要返回给本次调用方”——它请求的是当时的数据，返回旧值不是 bug，**污染缓存才是**。

## Alternatives considered

- 让起始版本“发起时不入缓存、结算时才入”：会顺带打掉命中复用（第二个缺陷族），因此改成
  「发起时入缓存 + 结算时**再**无条件写回」，这样命中复用仍然正确，只有失效竞态出错。
- 让检查去 `await` 一个没有结算的端口 promise：上一轮实测会让阶段超时（`exit=null`），
  现在每个在途调用都被显式结算。

## Consequences

- 困难档 5/12；核心题 29/48。
- 两次失败留下的教训写进制作口径：**缺陷必须真的制造出被测行为**（这一次是“写回”根本没发生），
  而验证器的“预期失败 vs 实际失败”比对是唯一能自动抓住它的闸门。
