# Agent Note: 题库加难方法论（跨实例不变量）

Status: implemented

## Problem

四份历史真实模型报告（`data/experiments/`，4 个模型各跑满 16 题）显示：16 道保留题里 11 道 4/4 全过、2 道 3/4，只有 CONC-04 与 ARCH-04 有分化且 ARCH-04 是 0/4。区难度区分度不足，根因不是断言太少，而是**现有检查都在单实例正确性层面**：照着契约实现一遍就能全过，不产生分化。

## Decision

加难的方向定为**跨实例一致性不变量**，而不是增加同类边界断言。以 CACHE-04 为样板：

1. 存储层引入版本判定：`readVersioned()` 返回内容派生的 epoch，`writeAtomicIfUnchanged(text, epoch)` 在版本不符时抛 `StaleWriteError` 且不改文件。
2. 缓存层缓存自己**最后确认过的** epoch，写回时带上它；被拒后立即重新装载最新版本，因此紧随其后的重试应当成功。
3. `recover(journal)` 补齐崩溃前已确认但未合并的条目。
4. 未实现 `VersionedStorage` 的存储走原语义，既有契约全部不变。

要点：**epoch 必须由内容或文件状态派生，不能是实例计数器**。第一版实现把 epoch 存在存储实例字段里，两个实例各有自己的计数器，落后写入照样通过了拒绝判定——这个缺陷是靠"用真实文件跑两实例交错"才暴露的，单元级内存存储测不出来。

替代实现按同一契约但结构不同（行数组 + 前缀拼接、mtime+size 派生版本、`#seen` 字段），在实现过程中也踩到同一个坑：每次写前重新读 epoch 等于总用最新版本，永远不过时；必须缓存初始化时读到的版本。

## Alternatives considered

- 只加更多边界断言：不产生分化，模型照样全过。
- 增加样本量或更大数据集：不能补足交互复杂度。
- 把所有题改成多进程：多数题的场景本身不需要，属于为难度而难度。

## Consequences

CACHE-04 由 13 项检查增至 17 项，版本升 0.3.0，新增四项检查全部可被起始缺陷检出。三向验证通过；三个 mutant 精确命中预声明检出项（publish-before-durable-write 额外交叉命中 public/state-write-failure，属有效检出、原样保留）。

方法论可复用：其余 12 道假难题按同样思路各加一层该题域特有的跨实例/跨进程不变量。难度标签仍以实测通过率校准，不因本次加难预先改写。

## 复合复杂度：给题目加第二个子系统（2026-10-18）

单点加检查会迅速变成军备竞赛。实测证据：API-04 已有 35 项检查、deepseek-flash 仍要 549 秒完成并通过；CACHE-04 288 秒通过。这些不是"测得不严"，是模型确实有能力。继续堆同类断言收益递减。

改用**复合复杂度**：给题目加第二个必须与原子系统保持一致的子系统，难度来自跨子系统的交互面。

CACHE-04 升 0.4.0 的做法：缓存增加二级索引（index()/keysFor()）。索引天然是条目的派生视图，一旦实现成"独立维护 + 手工同步"，就会在三个真实路径上分叉——崩溃在两次写之间、写入被版本判定拒绝、恢复重放遗漏同步。

判别力已验证：一个**看似合理但漏掉同步**的实现（索引缓存在字段里、只在提交时重建）被三条检查同时检出，而完全派生的实现 4/4 通过。这正是真实区分度的来源。

THR-04 的教训（同轮）：先做了"票据所有权"，实测发现 #stop 已经终止被取代代的 worker，旧代根本走不到发布分支，新检查是冗余防线。连续两个 mutant 都检不出来。已完整回退，不留无效检查。**加难前必须先做行为探测，确认"这一层真的没有防线"**，否则写完整套资产才发现不成立。

## 第三道：GRAPH-04 发布订阅（0.3.0）

同一种复合复杂度手法用在图上：DependencyWorkspace 增加 subscribe()。订阅必须是「跟着已提交的发布走」，而不是「跟着工作走」——这正是会分化实现的地方：把 prepare 完成当成发布通知、或先通知再落状态，都会让订阅者读到错误的视图。

判别力验证：构造「准备完成即通知」的实现，被两条检查检出，参考与替代实现全过。检查本身也修正过一轮——最初只断言监听器收到的参数，无法区分通知与发布状态的先后；改为在监听器内调用 snapshot() 读取**已发布状态**后才具备判别力。这是本轮最重要的方法论收获：**断言要观测发布状态，不能只观测回调参数**。

## LIFE-04 尝试与回退

尝试给 ProcessAcceptance 加并发槽位与排队。参考实现做出来了（默认单槽保持忙则拒绝，maxConcurrent>1 才排队），但**替代实现无法在合理时间内收敛**：用票据集合 + 等待队列的写法反复死锁，需要修正入队条件与泵送循环两处，最后仍无法稳定通过全部既有检查。

已把 LIFE-04 完整回退到基线并重新验证通过，不保留半成品。记录这个教训：**替代实现是加难成本的真正瓶颈**——它不是「再写一遍」，而是必须用不同结构满足同一契约。一个需要多轮试错才写对的替代实现，说明这个不变量本身对实现方式过于敏感，不适合作为判据。

衡量标准修正：新增不变量只有在**参考与替代两种结构都能自然满足**时才成立；若某条检查需要替代实现反复调试，那是检查过严，不是候选能力不足。
