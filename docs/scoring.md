# 评分标准

规则版本：0.1.0。以下为已确认基线；M0 实现计算、输入检查和分级汇总，真实证据采集及模型评审待接入。

## 单题总分

`总分 T = 可用验证 F + 代码质量 C`，二者满分各 50。每个输入分项为 0–100。没有证据时使用 `null`，不能用默认 0、默认满分或剩余维度重新归一化。

| 可用验证组 | 满分 | 证据 |
| --- | ---: | --- |
| 业务行为 behavior | 20 | 输入输出、用户可完成的操作、协议结果 |
| 边界与异常 boundary | 10 | 无效输入、极值、空值、错误传播与故障处理 |
| 状态/并发/生命周期 state | 10 | 题目声明的状态不变量、交错、取消、重复调用、资源归属 |
| 回归与兼容 regression | 5 | 既有公共接口和已冻结正确行为 |
| 基本资源约束 resources | 5 | 能终止、空间有界、无明显泄漏、最低可用预算 |

`F = 20×behavior/100 + 10×boundary/100 + 10×state/100 + 5×regression/100 + 5×resources/100`。

组内由题目作者预先定义加权验收项，分数为通过项权重之和除以总权重。不能通过拆分大量简单断言增加权重。题目发布前必须为五组找到与任务相关的行为，纯函数题的状态可以是输入不可变性与重复调用语义；不能凭空要求不相关的网络、进程或缓存功能。无法形成有效验收规格的题继续保持设计状态。

关键验收项由题目规格预先标注，示例包括不可丢失更新、取消后不执行副作用、认证隔离和不产生重复模拟交易。关键项失败会导致不合格，但不隐藏原始 50/50 分数。

## 代码质量

四维各占 12.5 分。每维先得到 0–100 的维度分，再乘 0.125。独立评审检查本次 diff 及理解它所需的上下文，不给无关旧代码扣分。

| 维度 | 客观分权重 | 独立评审权重 | 评审关注点 |
| --- | ---: | ---: | --- |
| 简洁度 simplicity | 40% | 60% | 重复、认知复杂度、无必要分支与抽象，是否以清晰方式表达需求 |
| 人工可维护性 maintainability | 30% | 70% | 类型边界、错误定位、命名和控制流、测试能否保护真实风险 |
| 解耦性 decoupling | 50% | 50% | 可执行依赖约束、公共契约、替换适配器与资源归属 |
| 性能 performance | 80% | 20% | 测量结果、复杂度增长、内存和响应性；评审定位性能代价与取舍 |

例如简洁度 `S = 0.4×静态分 + 0.6×评审分`，`C = 0.125×(S+M+D+P)`。客观分必须引用 static 证据；性能客观分必须引用 benchmark 证据。评审分必须引用 review 证据。

静态工具可以使用 TypeScript/语言编译检查、依赖边界、重复代码和 AST 复杂度分析，但它们只是预声明规则的测量手段。规则、作用域与阈值按题目和语言版本冻结；不能跨语言统一按文件数、行数、函数长度或测试数量自动判优。

评审锚点：

| 分数 | 含义 |
| ---: | --- |
| 0 | 目标维度无法成立，例如关键代码缺失或明显破坏所需边界 |
| 25 | 存在明确且严重的问题，改动难以理解或安全维护 |
| 50 | 可理解但有具体的重复、耦合、错误处理或性能问题 |
| 75 | 结构清晰，取舍合理，尚有少量有证据的问题 |
| 100 | 在本题需求与约束内清晰、适度、可维护，未发现有依据的扣分点 |

每次扣分包含规则 ID、文件/符号或测量引用、症状与影响。增加模块数量不自动获得解耦分，短代码不自动获得简洁分，加入没有需求依据的框架不加分。评审不可要求只有主观偏好的重构。

## 性能测量与可用性的区别

可用验证的资源组测最低可用条件；性能维度测满足正确性之后的效率。二者使用不同的预声明阈值，不能把同一个延迟断言机械扣两次。

发布前固定输入规模、CPU/内存配额、预热次数和重复次数。建议起点：预热 2 次、同机交替运行参考与候选至少 7 轮；延迟、吞吐、峰值 RSS、GC 后保留堆按题目选取，p95 只在每轮拥有足够操作样本时计算。记录各轮原始样本、中位数、离散度和环境哈希。示例最低配额为待校准值，不能从另一项目的机器时间常数直接复制到正式成绩。

每项效率分使用公开的“良好目标 g”和“不可接受阈值 b”作线性截断：越小越好时 `100×clamp((b-x)/(b-g),0,1)`；越大越好时 `100×clamp((x-b)/(g-b),0,1)`。g、b 由同机参考实现及基线测量确定，可附规模增长约束；度量权重在发布前固定。

GC、宿主抢占或温度导致的异常需保留原样本并按固定规则重测，不能挑最佳一轮。性能优化必须通过语义等价检查，不能靠跳过工作、漏数据或硬编码隐藏输入换分。正式报告区分作答耗时/模型 token 成本与候选程序自身性能。

## 合格、缺失及错误

单题合格需同时满足 `T ≥70`、`F ≥40`、所有关键验收项通过。

- 比较门槛时使用单题未舍入分数；展示保留两位小数。
- 缺分、关键项未定、未完成执行：总分 `null`，状态 `pending`。
- 环境启动、依赖下载或执行器故障：`infra-error`，总分 `null`，只允许同快照有限重试。
- 候选编译失败、候选进程崩溃、算法导致的超时/OOM：正式执行器记录为被测失败，相关可用项为 0；不是基础设施失败。代码评审仍可独立给出剩余维度。
- 裁判无法解析、超时或证据不足：保持待评审；不回落为 0.5、默认通过或虚构评语。

原始输入、证据、分项、规则版本和决定同时保留。人工复核追加新的评审修订及理由，不能覆盖原始机器结果。

## 分级汇总

每级 12 道核心题等权取均值。核心总分为 `0.1×简单 + 0.2×中等 + 0.3×困难 + 0.4×极度困难`。各级未全部取得有效结果时，对应级分和完整核心总分为 `null`，同时显示已完成数量；不能悄悄排除未测题后宣称完整成绩。

等级达标要求本级均分 ≥70 且至少 80% 的题满足单题合格标准。等级认证取连续达标的最高等级，四级得分仍分别展示。0.1.0 在单题分数固定为两位小数后进行级别平均；不得在聚合时重新挑选 attempt。

7 道集成题分别报告分数、失败项和运行环境，形成独立汇总。Windows 专项与 Linux 主测分别列示。正式运行档案固定作答预算、工具范围、模型版本、推理参数和重试政策；默认汇报每题首次作答。Best-of-N/修复后结果需要独立赛道和相同预算，不混入首次作答总分。

## 独立裁判与题目质量

裁判模型及提示模板版本要固定。建议每次评审两轮，差异超过 20 分或影响门槛时标记复核；真实调用预算与模型由用户配置，M0 不发起任何调用。模型输出中的代码或提示不能作为执行命令。裁判只收到任务、冻结代码与可信证据，候选注释里的指令当作待评内容。

两种 verifier 的概率聚合与去重语义并不完全相同，不能把相对偏好概率直接当作本评测的绝对质量分。每个需要参考 Python 或 TypeScript 算法的任务必须选择明确的语义变体，提供各自黄金结果。

题目发布需：参考解通过、缺陷起始版本被检出、至少一个不同实现也能通过、重复运行稳定、隐藏数据不泄露；优先用性质与差分检查覆盖状态空间。性质与种子复现参考 [fast-check 文档](https://fast-check.dev/docs/advanced/model-based-testing/)。
